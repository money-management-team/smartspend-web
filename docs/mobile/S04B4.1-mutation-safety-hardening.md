# Mobile mutation safety hardening (S04B4.1)

A hardening pass over the two Mobile writes S04B4 introduced (a new category, and a rename of your own; see [S04B4-category-management.md](S04B4-category-management.md)). No new endpoint, no new write, nothing about money. The backend repository was not available at the time, so **the backend effects of both writes were UNVERIFIED** (§11). Update 2026-11-01: they are now checked against the source (no side effects beyond the row; a duplicate gives 422), and a duplicate 422 on create now refreshes the list. See BACKEND-VERIFICATION-RESULTS.md §4 and §8 (M1).

## 2. Changes made

- `categories/useLeaveGuard.js` (new): React Router's `useBlocker`, the presentation guard and `beforeunload`, for the category forms only.
- `categories/MobileCategoryForm.jsx`: the leave question is driven by the router blocker (Cancel is now a plain navigation that the guard holds); focus is remembered and restored; a second question while sending; the "changed" outcome.
- `models/categoryForm.js`: `classifyOutcome(error, operation)` with a per-operation contract table (§4).
- `categories/useCategoryMutation.js`: identity re-check on every error; a `stillCurrent` check for the workspace; the "changed" phase; the status kept for the unknown reason.
- `categories/CategoryOutcome.jsx`: a reason line for unknown outcomes; the "changed" outcome.
- `i18n/messages.js`: new strings (leave-while-sending, reasons, workspace changed), rename-consequence wording, removed the three "Nothing was saved" texts for statuses that are no longer refusals. English and Arabic keep exact key parity.
- `styles/mobile.css`: app-bar title layout (§7), leave-dialog buttons.
- Tests: the Mobile harness now runs on a **memory data router**, like the app; new `mobileCategoryNavigation.test.mjs`; the category model, screen and identity tests updated to the new policy.
- No Desktop file, shared component, API client, AuthProvider or backend file was changed.

## 3. Navigation protection

`useLeaveGuard(active)`, with `active = (dirty and editing) or submitting`:

| Way out | Behaviour | Test |
|---|---|---|
| Bottom bar | held; question; Keep editing / Discard changes | ✔ |
| Compact menu (Menu + Add) | choosing a destination closes the menu, then the question (one dialog at a time) | ✔ |
| In-page Back links, the form's Cancel | held; same question | ✔ |
| Browser Back and Forward | held (the data router intercepts POP) | ✔ both |
| Keyboard (a focused link activated) | held like a tap; Escape in the question = Keep editing | ✔ |
| Automatic presentation switch (another tab picks the full version) | waits: the form registers with the presentation guard, and the redirect itself would also be held by the blocker | ✔ |
| Rename form | the same | ✔ |
| Request on its way | held with a different question: "This is still being sent. Leaving won't stop it, and you won't see its result here." (Stay and wait / Leave anyway) | ✔ |
| Answer arrives while the question is open | the question is withdrawn and the outcome shown | ✔ |
| Clean form, a name typed back to the original, after a confirmed or unknown outcome | not held | ✔ |
| Identity changes while the question is open | the boundary removes the form, its draft and the question | ✔ |
| Reload, closing the tab | the browser's own `beforeunload` prompt is armed while active; **best effort**: the browser decides whether to show it, and no custom dialog can appear there | not testable in jsdom |
| The OS ending the browser | **nothing can be done** | — |

Rules: only a change of page is held (the query or hash of the same page never is); Discard continues to exactly the requested destination (proceed); Keep editing resets the held navigation and returns the focus to the field the person was in; a decision is taken once (two fast taps on Discard are one navigation, tested by going Back afterwards and finding exactly one new history entry); the held intent is cleared after use by the router itself. Leaving while sending is never claimed to cancel the request.

## 4. Outcome classification

`classifyOutcome(error, operation)` in `models/categoryForm.js`. "Rejected" only where the documented contract ([../categories/api.md](../categories/api.md)) names the status for that operation; everything else is "unknown". Backend source unavailable, so even the rejected rows rest on documentation, not code.

| Result | Create (`POST /categories`) | Rename (`PATCH /categories/{id}`) | Basis |
|---|---|---|---|
| 2xx, the server's category matches what was sent (id, name, type, not system, same workspace) | **confirmed** | **confirmed** (same id, new name) | the answer itself |
| 2xx, category missing or different; not JSON; failure envelope with a success status | unknown | unknown | may have been applied |
| 400 | unknown | unknown | not documented |
| 401 | unknown → the app's 401 flow clears the session, and the identity check then shows the session notice instead of any result | same | where the token is checked is not verified |
| 403 | **rejected** | **rejected** | documented: system category / not manageable |
| 404 | unknown | **rejected** | documented for one category ("doesn't exist or isn't yours"); not for the create |
| 408 | unknown | unknown | rule 1; and Chrome may already have resent the POST by itself (§9) |
| 409 | unknown | unknown | no category meaning is documented |
| 422 | **rejected** (field errors shown) | **rejected** | documented validation of `name`, `type`; backend unverified |
| 429 | unknown | unknown | a rate limit may sit before or after the work; not verified |
| 5xx | unknown | unknown | |
| timeout, network, abort | unknown | unknown | an aborted or timed-out request may still be processed |
| identity changed (before, during or after) | nothing shown; the identity notice | same | |
| workspace changed while on its way | **changed**: not presented as this screen's result; checks only | n/a (the rename is by id) | |

"Rejected" also requires that the error is the API client's own `ApiError` with the matching code. Unknown outcomes show a reason line (asked to slow down / reported a conflict / no answer in time / a problem answering / the answer didn't say) and the same advice: check before trying again. Nothing is sent again by itself; no idempotency key is sent (the category endpoints have none); a later list that contains a similar name is never treated as proof.

## 5. Identity safety

The guard is asserted in the same turn the request leaves and again when the answer arrives; **on every error the identity is re-checked before the error is classified**, so a 401 (which clears the session) or an answer after a sign-out or switch never shows a result. Tested: sign-in as B or sign-out in another tab before the tap (nothing sent) and while the request is on its way (nothing shown); a change with no event, caught on arrival; a 401 in flight; blocked storage; two fast clicks before React re-renders (one request); leaving during submission (no result shown, nothing resent, the list read fresh); a late answer after the person moved to another category's form; a remount after an unknown outcome (a fresh empty form, nothing resent); a new session in the tab; the workspace changing in flight ("changed"). No token, payload or category data is stored. No shared Desktop change was needed; the Desktop AuthProvider's missing cross-tab listener remains a separate approval item.

## 6. Category rename consequences

What the repo documents: transactions reference a category by id; the name is shown wherever the category is shown. The page and the form now say: "Changing its name may also change how existing transactions using it are labelled." No claim is made that a rename changes no ledger data, no balance, or has no financial side effects. Type changes, archive, icon and colour editing and deletion stay out of Mobile.

**Found in this run: Chrome resends a POST by itself after a 408.** Two jobs that answer the create with `408 Request Timeout` recorded **seven** `POST /categories` at the mock server. A page-level counter showed the app called `fetch` **once**; a 422 in the same setup arrived once. The repeat happened in Chrome's network layer, with and without `Connection: close`, and no JavaScript can turn it off. The Mobile screen still showed the unknown outcome and sent nothing itself. Consequence: **if the backend or a proxy ever answers a category create with 408, the browser itself may create the category several times.** This is a platform behaviour, not a Mobile defect; it applies to the full version's forms too. It can only be fixed on the server side (never answer 408 to these writes after accepting the body, or make the create idempotent). Added to §11 and §12.

Found by looking at the screenshots and fixed: at 2× text on 320 px the dialog's "Discard changes" overflowed its half-width button (both answers are now full width).

## 11. Backend uncertainties

Still **UNVERIFIED**. Questions and where the answer would be found in a Laravel backend (names to look for, not claims about this repository):

1. Does `POST /categories` touch any ledger table, balance, budget or job? — the category store action in the categories controller, its form request, the `Category` model's events/observers, and any listener on a "category created" event.
2. Does a rename do anything besides update the row? — the update action, `Category` observers (`updating`/`updated`), any cache, search index or AI-rule sync.
3. Does a rename change how historic transactions are interpreted (reports keyed by name, exports, AI training)? — report queries that group by category name vs id; export builders.
4. Duplicate names: is there a unique rule (per workspace, per type, case-insensitive?) and what does it return? — the store/update form requests' `rules()`, database unique indexes in the categories migration.
5. Which statuses can these endpoints return, and does any of 409/408/429/5xx happen after the row is written? — exception handler, middleware order (throttle before or after the controller), transaction boundaries in the actions.
6. Authentication and authorization: where is the token checked, and is the 403 a policy check before any write? — route middleware groups, the category policy.
7. Can a result be reconciled reliably (a client-supplied key, a unique constraint, a creation id)? — the store action and migration.
8. Ownership and workspace scoping: is `workspace_id` checked against the user's memberships, and is a category ever shared across workspaces? — the form request, the policy, the model's global scopes.
9. Can a create complete after the client gave up (a 20 s client timeout)? — request time limits, queued work, database transaction scope.
10. **Can these routes ever answer 408** (the app server, a reverse proxy, a load balancer, the hosting provider's front end)? Chrome resends a POST by itself after a 408 (§9), so a 408 there could create duplicates. — web server and proxy timeout configuration, hosting documentation.

No live endpoint was called. If an authorized local or staging backend becomes available, these are the checks to run there first.

## 12. Remaining blockers

- Backend verification (§11) before Mobile writes are enabled anywhere real.
- **Browser-level resend after 408** (§9): the app sends once, but Chrome itself repeated the POST six more times in this test. Outside the app's control; needs a server-side answer (no 408 for these writes, or an idempotent create). Until then a 408 can mean duplicate categories.
- Reload/close protection is best effort (browser prompt); the OS ending the browser is unprotectable.
- A `changed` (workspace) outcome is detected only when the stored workspace changes; a workspace switch that does not change storage is not seen.
- The create and outcome screens follow the S04B4 screen specification, not an approved design.
- Unchanged from earlier phases: no live-API verification of any Mobile screen; the `experienceRendering` finding stays PARTIAL; the Desktop AuthProvider cross-tab listener needs approval; no real-device or assistive-technology testing.
